# Система мониторинга ликвидности

**Система раннего предупреждения стресса ликвидности рублёвого денежного рынка**

Учебный проект по практике | Группа М8О-102СВ-25 | ПСБ Казначейство, 2026

---

## Что это такое

Это система, которая автоматически собирает публичные данные с сайтов ЦБ РФ, Минфина и Росказны, рассчитывает по ним сигналы стресса ликвидности и агрегирует всё в один индекс - **LSI (Liquidity Stress Index, 0–100)**. Чем выше LSI, тем сильнее напряжение на денежном рынке.

Проект построен по техническому заданию ПСБ Казначейства. Идея в том, что казначей банка не должен вручную мониторить десятки источников - система делает это сама и показывает итог на дашборде.

## Как запустить

```bash
# 1. Установить зависимости
pip install -r requirements.txt

# 2. Запустить дашборд
python app.py

# 3. Открыть в браузере
http://localhost:8050
```

При первом запуске система загрузит данные из источников и сохранит их в `data_cache.db`. При следующих запусках берёт из кэша и подгружает только новые данные.

Если нужно обновить данные принудительно - удалить файлы `data_cache.db` и `.cache_checked` и запустить снова.

## Пять модулей

Система состоит из пяти независимых расчётных блоков. Каждый собирает данные из своего источника, рассчитывает сигналы и нормализует их через MAD (Median Absolute Deviation) - это стандартный способ сравнить показатели с разными единицами измерения.

### М1 - Усреднение обязательных резервов

**Что это:** Банки обязаны держать на корсчетах в ЦБ среднедневной остаток не ниже норматива. Когда фактические остатки сильно превышают обязательные - это сигнал, что банки заранее накапливают буфер, опасаясь нехватки ликвидности.

**Источники данных:**
- Excel с историей резервов с 2004 года: `cbr.ru/vfs/hd_base/RReserves/required_reserves_table.xlsx`
- RUONIA (ставка межбанковского рынка): `cbr.ru/hd_base/ruonia/`

**Что считает:**
- `MAD_score_spread` - насколько фактические остатки отклонились от нормы
- `MAD_score_RUONIA` - насколько выросла ставка межбанковского рынка
- `Flag_EndOfPeriod` - флаг последних дней периода усреднения

**Вес в LSI: ~20%**

---

### М2 - Аукционы репо ЦБ

**Что это:** Когда у банков не хватает денег, они идут на аукционы репо ЦБ - берут деньги у регулятора под залог ценных бумаг. Высокий cover ratio (спрос сильно превышает размещение) и ставка, близкая к верхней границе коридора - классический сигнал стресса.

**Источники данных:**
- История аукционов: `cbr.ru/hd_base/repo/`
- Ключевая ставка: `cbr.ru/hd_base/keyrate/`

**Что считает:**
- `cover_ratio` = объём спроса / объём размещения
- `rate_spread` = ставка аукциона − ключевая ставка
- `MAD_score_cover`, `MAD_score_rate_spread` - нормализованные отклонения
- `Flag_Demand` - флаг переспроса (cover > 2.0)

Фокус - на 7-дневных аукционах как основном инструменте.

**Вес в LSI: ~25%**

---

### М3 - Размещение ОФЗ

**Что это:** Когда у банков мало свободных денег, они не могут покупать ОФЗ на аукционах Минфина - cover ratio падает ниже 1.2. Это прямой сигнал дефицита ликвидности.

**Источники данных:**
- Результаты аукционов Минфина (автоматически скачиваются Excel-файлы): `minfin.gov.ru`
- Пресс-релизы ЦБ для проверки: `cbr.ru/press/pr/`

**Что считает:**
- `cover_ratio` = объём спроса / объём предложения
- `MAD_score_cover` - нормализованное отклонение
- `Flag_Nedospros` - флаг недоспроса (cover < 1.2)
- `Flag_Perespros` - флаг переспроса (cover > 2.0, избыток ликвидности)

**Автоматизация:** система сама находит и скачивает актуальные Excel-файлы с сайта Минфина, не нужно класть их вручную.

**Вес в LSI: ~20%**

---

### М4 - Налоговый период и сезонность

**Что это:** В налоговые недели клиенты банков (юрлица и ИП) снимают деньги со счетов для уплаты налогов. Это вызывает предсказуемый сезонный отток ликвидности. М4 работает не как отдельный сигнал стресса, а как **мультипликатор** - усиливает сигналы других модулей именно в эти периоды.

**Источники данных:**
- Налоговый календарь ФНС (ЕНП, НДС, налог на прибыль, страховые взносы): `nalog.gov.ru/rn77/calendar/`
- Исторические данные из М1, М2, М5 для расчёта `seasonal_factor`

**Что считает:**
- `Tax_Week_Flag` (0/1) - флаг налоговой недели
- `End_of_Month_Flag` (0/1) - конец месяца
- `End_of_Quarter_Flag` (0/1) - конец квартала
- `Seasonal_Factor` (1.0–1.4) - мультипликатор на агрегационном слое

**Решение проблемы двойного счёта:** налоговый эффект уже частично отражён внутри М1, М2 и М5 - когда наступает налоговая неделя, RUONIA растёт, cover ratio репо ЦБ растёт, остатки на ЕКС меняются. Если добавить М4 аддитивно - получится двойной счёт. Поэтому М4 входит именно как **мультипликатор**, а не как слагаемое. Это подтверждается статистически: в налоговые периоды все ключевые показатели М1/М2/М5 действительно отклоняются от нормы, что видно на вкладке «Детали» в дашборде.

**Вес в LSI: мультипликатор, не суммируется**

---

### М5 - Средства федерального казначейства

**Что это:** Когда компании платят налоги или государство привлекает деньги через ОФЗ, деньги уходят с корсчетов банков на Единый казначейский счёт (ЕКС) - ликвидность «утекает» из системы. Когда казначейство размещает остатки обратно в банки - ликвидность возвращается.

**Три источника данных:**
1. **ЦБ bliquidity** - структурный баланс ликвидности банковского сектора (ежедневно): `cbr.ru/hd_base/bliquidity/`
2. **ЦБ SORS** - остатки средств федерального бюджета на счетах банков (ежемесячно): `cbr.ru/statistics/bank_sector/sors/`
3. **Росказна** - данные аукционов по размещению средств ЕКС на банковских депозитах (XML-файлы): `roskazna.gov.ru`

**Что считает:**
- `structural_balance` - структурный баланс (профицит/дефицит)
- `delta_weekly`, `delta_monthly` - изменение за неделю и месяц
- `federal_budget`, `extrabudget_funds` - остатки из SORS
- `eks_volume`, `eks_rate` - объём и ставка размещений на депозитах
- `banks_total`, `banks_accepted` - количество банков-участников аукционов
- `MAD_score_structural`, `MAD_score_delta`, `Flag_Budget_Drain`

**Техническая деталь:** Росказна не принимает стандартный SSL-сертификат Python - сайт использует российский удостоверяющий центр. Решение - `verify=False`. Данные публикуются в XML-файлах (не Excel), парсинг через `xml.etree.ElementTree`.

**Вес в LSI: ~15%**

## Агрегация и модель LSI

**Метод: Gradient Boosting (GradientBoostingRegressor из scikit-learn)**

### Почему GBM

В ТЗ разрешён любой ML-метод с обязательной интерпретируемостью. Мы выбрали GBM по следующим причинам:

- Умеет улавливать нелинейные взаимодействия между модулями (например, совпадение налоговой недели с оттоком казначейства - это не просто сумма двух сигналов)
- `feature_importances_` даёт понятное объяснение вклада каждого признака
- Параметры (неглубокие деревья `max_depth=2`, `subsample=0.8`) снижают риск переобучения

### Как обучается

Размеченной выборки нет, поэтому таргеты задаются вручную на основе известных исторических эпизодов:

| Период | Событие | Таргет LSI |
|--------|---------|------------|
| Декабрь 2014 – январь 2015 | Ставка 17%, паника | 90 |
| Февраль–апрель 2022 | Санкции, обвал рубля | 92 |
| Август–октябрь 2023 | Девальвация, экстренное заседание ЦБ | 78 |
| 2016, 2019, 2021 | Спокойные периоды | 18–22 |

Модель обучается предсказывать эти таргеты по MAD-признакам из всех модулей, затем нормализует предсказание в шкалу 0–100. После нормализации применяется `seasonal_factor` из М4 как мультипликатор.

### Вклад модулей

Интерпретация через `feature_importances_` - встроенный механизм GBM. Вклад каждого модуля виден прямо на дашборде. Пример типичного распределения: М2 (репо) вносит наибольший вклад, поскольку это самый оперативный ежедневный сигнал.

### Пороги статусов

| LSI | Статус |
|-----|--------|
| 0–40 | Норма |
| 40–70 | Повышенный стресс |
| 70–100 | Высокий стресс |

## Бэктест

Обязательное требование ТЗ - проверка на трёх исторических эпизодах стресса.

| Эпизод | Средний LSI | Максимальный LSI |
|--------|-------------|------------------|
| Декабрь 2014 (ставка 17%) | ~26 | ~62 |
| Февраль 2022 (санкции) | ~48 | ~100 |
| Август 2023 (девальвация) | ~48 | ~100 |

**Специфичность в спокойные периоды** (доля дней с LSI < 45):
- 2016: 96%
- 2019: 85%
- 2021: 89%

Результаты видны на вкладке «Бэктест» в дашборде.

## Дашборд

Дашборд написан на Dash (Plotly). Состоит из нескольких страниц:

- **Главная** - текущее значение LSI, статус, активные флаги, вклад модулей
- **Графики** - динамика LSI и отдельных сигналов за выбранный период
- **Бэктест** - сравнение системы с историческими стресс-эпизодами
- **Детали модулей** - таблицы и графики по каждому из 5 модулей
- **Цифровой помощник** - чат с LLM для вопросов по данным системы

## LLM-модуль (бонус)

Сделали бонусный модуль. Взяли Llama 3.3 70B через Groq - он бесплатный и отвечает быстро.

На главной странице есть кнопка, по которой генерируется текстовый комментарий по текущей ситуации - модель получает значение LSI, активные флаги и ближайшие события (налоги, аукционы) и пишет что происходит и чего ожидать.

На отдельной вкладке есть цифровой помощник - чат, где можно задавать вопросы по данным системы в свободной форме. Есть готовые быстрые вопросы на кнопках: «Что происходило в феврале 2022?», «Почему в декабре 2014 был стресс?», «Как налоговая неделя влияет на репо ЦБ?» и другие. Можно писать и свои. Модель знает историю диалога в рамках сессии, так что можно уточнять и переформулировать. Контекстом служат данные самой системы - LSI, сигналы модулей, флаги.

Чтобы это работало, нужно создать файл `.env` рядом с `app.py` и положить туда ключ:
```
GROQ_API_KEY=ваш_ключ
```

Ключ бесплатный, регистрация на console.groq.com. Если ключа нет - всё остальное работает, просто LLM не отвечает.

## Кэш и хранение данных

Данные хранятся в SQLite-базе `data_cache.db`. Логика работы:

1. Если сегодня уже запускались - берёт всё из базы, не парсит
2. Если база есть, но устарела - догружает только новые данные (инкрементально)
3. Если базы нет - полный парсинг с нуля

Это важно, потому что полная загрузка занимает несколько минут - кэш ускоряет повторные запуски до секунд.

Если добавляются новые колонки в модули (меняется схема) - нужно удалить `data_cache.db` и `.cache_checked` и запустить снова.
